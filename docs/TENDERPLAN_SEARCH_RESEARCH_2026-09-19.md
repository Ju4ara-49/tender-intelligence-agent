# Глубокое исследование формы поиска TenderPlan

Дата фиксации: 2026-09-19

Цель: зафиксировать только различающиеся возможности формы поиска TenderPlan и превратить их в требования к нашему SearchProfile/Web UI. Брендинг, цвета, тексты и точная компоновка TenderPlan не копируются.

- Официальная школа, инструкция по ключам: https://tenderplan.ru/school/kak-najti-tendery-v-tenderplan/

- Официальный FAQ школы: https://tenderplan.ru/school/faq2/

## Уже есть в нашем проекте — не дублировать
- имя профиля/ключа;
- ключевые слова;
- слова-исключения;
- регионы;
- наши площадки;
- НМЦК от/до;
- наличие аванса и минимальный процент аванса;
- максимальный срок постоплаты;
- минимальный срок до окончания подачи;

- обеспечение контракта от/до;
- минимальный AI score;
- сохранение профиля через SearchProfileStore.

## Новые элементы формы

### 1. ОКПД2
Отдельный классификатор, независимый от keywords. Нужен множественный выбор кодов, поиск по коду/названию и явное состояние «не задан». По официальной инструкции ОКПД2 применяется для 44-ФЗ и 223-ФЗ.

### 2. Тип закупки / режим процедуры
Отдельный блок, не смешивать с ЭТП. Зафиксированы: 44-ФЗ; 223-ФЗ; 615-ПП РФ/капремонт; коммерческие; план-графики; продажа имущества/банкротство.

### 3. План-график
Отдельный режим: не учитывать / включить вместе с обычными закупками / только план-графики. Это поиск будущего спроса до публикации закупки.

### 4. Банкротство / продажа имущества
Отдельный тип процедуры, не смешивать с обычными коммерческими закупками.

### 5. Иерархия региона
Поддержать страна → федеральный округ → регион. Нужны действия «Выбрать все» и «Сбросить все». Каноническое хранение конкретных регионов сохранить.

### 6. Заказчик
Отдельный фильтр по названию или ИНН, с несколькими заказчиками и поисковым шаблоном. Исключение заказчика добавлять только после появления реального backend-контракта.

### 7. Поиск внутри документации
Текущий checkbox в нашем web_ui disabled и всегда checked — это fake capability. Его надо сделать реальным. Разделить поиск в основных данных и документации.

### 8. Отдельные ключевые слова документации
Экспертный режим TenderPlan позволяет задавать отдельные слова для документации и искать их отдельно или совместно с основным запросом. Модель должна предусмотреть document_keywords и режим поиска. Если backend не умеет применять это, UI не должен притворяться, что умеет.

### 9. Спецоператоры keywords
Зафиксировать в едином query contract и подсказке UI: пробел = AND; запятая = OR; * после основы = формы слова; кавычки = точное соответствие; (слово1 слово2)~N = допустимое расстояние между словами; обычные слова получают окончания автоматически согласно официальной инструкции.

### 10. Отраслевые пресеты
Есть «Выбрать отрасль», автоматически заполняющий keywords и exclusions. Для нашего проекта нужен каталог пресетов, который пользователь может изменить до сохранения. Несколько отраслей не объединять автоматически в один профиль.

### 11. Место поставки
Экспертный режим отдельно упоминает место поставки. Не смешивать его с регионом поиска. Нужен отдельный delivery_place.

### 12. ЭТП
Разделить наши collectors/источники и фильтр конкретной ЭТП. По официальному FAQ выбор конкретной площадки в экспертном режиме относится к коммерческим/банкротным секциям; 44-ФЗ/223-ФЗ в этой логике отдельно не выбираются.

### 13. Способ проведения
Отдельный фильтр procurement_method. Не смешивать с законом, типом закупки и ЭТП.

### 14. Преимущества / СМП
Отдельный фильтр: не учитывать / СМП / без СМП. Другие преимущества добавлять только после реального backend-контракта.

### 15. Архитектура «ключа»
Главная идея: поиск — сохранённый ключ, а не одноразовый запрос. В нашем проекте канонический объект — SearchProfile. Он должен иметь имя, критерии, enabled, сохранение, повторное использование, редактирование, дублирование, удаление, запуск и историю запусков.

## UX-принципы
1. Progressive disclosure: простой поиск → экспертные поля.
2. Пустой фильтр ничего не ограничивает.
3. Семантически разные фильтры не смешивать.
4. Результат должен объяснять релевантность: keywords, ОКПД2, регион, закон, НМЦК, обеспечение, аванс, срок, СМП, источник/ЭТП.
5. Специализированные профили лучше гигантского универсального запроса.
6. UI не показывает fake capability.
7. Для каждого нового поля: модель → persistence → backend contract → tests → UI.
8. SearchProfile остаётся источником истины для Web UI, Telegram и orchestrator.

## Что НЕ копируем
- логотип/название TenderPlan;
- цвета и точную визуальную тему;
- пиксельную компоновку;
- маркетинговые тексты;
- закрытые алгоритмы поиска;
- неподтверждённые заявления о качестве поиска.

## Приоритет внедрения
P0: ОКПД2; тип закупки; план-график; банкротство/имущество; заказчик; настоящий document-search toggle; operators/help; экспертный режим.
P1: document_keywords; место поставки; способ проведения; ЭТП с нормализацией по типу процедуры; СМП/преимущества; страна/округ/регион; отраслевые пресеты.
P2: объяснение релевантности в результатах; аналитика профиля/выборки; workflow вокруг сохранённых ключей.

## Критерий готовности
Функция считается внедрённой только при цепочке UI → form parsing → SearchProfile → SQLite → TenderCriteria/канонический search contract → реальная фильтрация/collector, где применимо → tests. Если источник пока не умеет фильтр, это должно быть явно отражено контрактом и тестами; UI не создаёт ложное впечатление.

## Подтверждённые выводы
Официальная публичная форма подтверждает keywords, exclusions, document search, округ/регион, ОКПД2, 44-ФЗ/223-ФЗ/коммерческие/план-графики, заказчика, начальную цену, обеспечение заявки/контракта и аванс. Официальная инструкция подтверждает специальные операторы keywords и сохранённые ключи. Официальная статья про экспертный режим добавляет отдельные слова документации, интервал между словами, место поставки, конкретные площадки, способ проведения и преимущества/СМП.
